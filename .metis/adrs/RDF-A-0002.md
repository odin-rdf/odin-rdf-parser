# ADR-2: Term representation: tagged union with value semantics

## Context

The Core RDF Data Model initiative (RDF-I-0001) must fix the Odin representation of RDF terms — IRIs, blank nodes, literals, and RDF-star triple terms — before triples, quads, and the parser API (RDF-I-0002) can be shaped. ADR RDF-A-0001 already constrains the design: term strings are **borrowed slices by default**, so whatever the term type is, it must carry `string` slices directly and be cheap to copy and pass by value; lifetime lives in a documented contract, not in the type.

The forces at play:

- **Type safety vs. uniformity**: a term is exactly one of four kinds; consumers switch on the kind constantly (emitters, stores, comparators).
- **RDF-star recursion**: a triple term contains a triple, which contains terms — the type is self-referential and needs indirection somewhere.
- **RDF 1.2 literals**: a literal has a lexical form and datatype, optionally a language tag (`rdf:langString`) and, new in RDF 1.2, a base direction (`rdf:dirLangString`).
- **Quad graph labels**: only an IRI or blank node may name a graph (plus "the default graph"); a full `Term` there would admit invalid states.
- **Downstream stores** will re-encode terms as fixed-size interned IDs regardless — the parser-facing type does not need to be the storage type.

## Decision

Terms are represented as an **Odin tagged union over per-kind types, with value semantics** — a `Term` is a small copyable value whose strings are borrowed slices per RDF-A-0001. Sketch (final naming settled in RDF-I-0001):

```odin
IRI        :: distinct string
Blank_Node :: distinct string   // label without the leading "_:"

Direction :: enum u8 { None, LTR, RTL }

Literal :: struct {
    lexical:   string,
    datatype:  IRI,        // always set; xsd:string when unadorned
    language:  string,     // empty unless datatype is rdf:langString / rdf:dirLangString
    direction: Direction,  // None unless datatype is rdf:dirLangString
}

Term :: union {
    IRI,
    Blank_Node,
    Literal,
    ^Triple,               // RDF-star triple term
}

Triple :: struct { subject, predicate, object: Term }

Graph_Label :: union { IRI, Blank_Node }   // nil = default graph
Quad :: struct { using triple: Triple, graph: Graph_Label }
```

Concretely:

1. **Tagged union, not kind-enum struct**: `Term` is an Odin `union`; consumers use type switches, and the compiler checks variant handling.
2. **`distinct string` for IRI and blank node**: type safety at zero representation cost; a blank node label is stored without the `_:` prefix (syntax, not identity).
3. **Literal carries RDF 1.2 fields**: lexical form, datatype IRI (always populated — `xsd:string` for plain literals), language tag, and base direction. Invariants tying language/direction to the `rdf:langString`/`rdf:dirLangString` datatypes are documented and enforced by constructors, not by the type.
4. **Triple terms via pointer**: the self-reference is broken with `^Triple`, allocated from an explicit allocator. Only RDF-star nesting allocates; ordinary terms never do. The type permits triple terms in any position; the RDF 1.2 grammars restrict them to object position, and parsers enforce that — the model does not.
5. **`Graph_Label` is a restricted union**: IRI or blank node, with `nil` meaning the default graph — invalid graph names are unrepresentable. `Quad` embeds `Triple` via `using`, so every quad is usable where a triple is expected.
6. **Value semantics throughout**: copying a `Term`, `Triple`, or `Quad` copies slice headers and the tag — no bytes, no ownership transfer. `clone`/intern (per RDF-A-0001) is the only deep-copy operation; for triple terms it also clones the pointed-to triple recursively.
7. **Equality and hashing are structural**: kind plus component-wise comparison of lexical content, recursing through triple terms. Two terms are equal iff they are the same RDF term, regardless of which buffer their slices borrow from.

## Alternatives Analysis

| Option | Pros | Cons | Risk Level | Implementation Cost |
|--------|------|------|------------|-------------------|
| Tagged union + value semantics (chosen) | Compiler-checked kind handling; idiomatic Odin; zero-alloc for non-star terms; slices fit borrow contract | Term size is max-variant (~literal, ≈40–56 B); triple terms need pointer + allocation | Low | Low |
| Struct with kind enum + overloaded fields | Uniform layout; no union tag semantics to learn | Field meaning depends on kind (invalid states representable); no compiler exhaustiveness help; same size anyway since Literal dominates | Medium | Low |
| Interned handles (terms are u32/u64 IDs into a table) | Tiny triples (12–24 B); fast equality/hashing; store-friendly | Requires a context object for every operation; forces interning of every term, defeating RDF-A-0001's zero-copy borrow-by-default; conflates parser model with storage model | High | High |
| No unified Term (distinct types + generics/overloading only) | Maximum static precision per position | RDF is heterogeneous at every position (subject: IRI/bnode/…); explosion of generic instantiations; awkward for dynamic consumers like stores | Medium | Medium |

## Rationale

- **The union is what the domain is**: an RDF term is a closed sum of four kinds; Odin's `union` states that directly and type switches over it read like the RDF spec's case analysis. The kind-enum alternative buys nothing (the Literal variant dominates size either way) and costs safety.
- **Interned handles belong to the store**: RDF-A-0001 established that downstream stores re-encode terms into their own fixed-size representation. Pushing interning into the core model would make every parse pay for a table the common streaming consumer doesn't need, and would break the "statement borrows from source until next `parser_next`" contract.
- **Pointer only where recursion forces it**: RDF-star nesting is the single place the type is self-referential and the single place term construction allocates. Real-world data makes triple terms rare, so the common path stays allocation-free — mirroring the copy-on-write escape decision in RDF-A-0001.
- **Constructors over type-level invariants**: Odin has no sum-type refinement to make "language implies rdf:langString" unrepresentable without splitting Literal into multiple variants, which would triple the union's surface for marginal gain. Documented invariants plus constructor enforcement is the idiomatic trade.
- **`Graph_Label` as its own union** is cheap precision: unlike the literal invariants, this one *is* expressible in one line and prevents a whole class of invalid quads.

## Consequences

### Positive
- Compiler-checked exhaustive handling of term kinds in every emitter, comparator, and store adapter.
- Constructing non-star terms allocates nothing; parsers can yield borrowed terms with zero overhead, per RDF-A-0001.
- Invalid graph labels are unrepresentable; quads reuse all triple-level code via `using`.
- The model is storage-agnostic: stores can layer interned IDs on top without the core carrying that machinery.

### Negative
- `Term` is max-variant-sized (the Literal footprint, roughly 40–56 bytes) even when holding a bare IRI; triples are ~3× that. Acceptable for a streaming model where statements are transient; stores compact on ingest.
- Triple terms allocate and require recursive clone/destroy/equality — the one place value semantics isn't free; deeply nested star data could recurse deeply (a documented depth limit in parsers may be warranted).
- Literal invariants (language ⇔ langString datatype) rest on constructor discipline; hand-built Literal values can violate them.

### Neutral
- Naming and exact field order are settled in RDF-I-0001, not here; this ADR fixes the *shape*, not the bikeshed.
- Equality being structural (buffer-independent) means hashing must also be content-based; any future interning layer can add pointer-equality fast paths without changing semantics.
- If profiling ever shows Term size hurting a hot path, a compact index-based statement representation can be introduced *inside* a parser or store without changing this public model.
