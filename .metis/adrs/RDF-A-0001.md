# ADR-1: Parser style: streaming pull parser with zero-copy slices

## Context

The [[odin-rdf-parser]] vision (RDF-V-0001) requires parsers for N-Triples, Turtle, N-Quads, and TriG, and names "streaming-friendly" as a core principle. The parser style must be decided before the first parser initiative is drafted (a prerequisite recorded in RDF-I-0001).

A driving downstream goal: a triplestore/quadstore will eventually be built on this library, with a reference implementation on LMDB, which offers zero-copy reads (values are stable views into memory-mapped pages for the lifetime of a read transaction). Even though the store will likely encode terms as fixed-size IDs rather than persist raw RDF text, the parser should be able to operate with the same zero-copy discipline: terms as slices of the source buffer, no materialization of the whole document.

RDF syntax constrains how far zero-copy can go, in three specific places:

1. **Escape sequences** (`\uXXXX`, `\"`, `\n`, …) in literals and IRIs mean the unescaped value is not a substring of the source. Escapes are rare in real-world data.
2. **Prefix and base resolution** (Turtle/TriG only): expanding `foaf:name` against the prefix map, or resolving a relative IRI against the base, produces a string that does not exist in the source. N-Triples and N-Quads have neither, so the line-based formats can be fully zero-copy.
3. **Slice lifetimes**: borrowed slices require the underlying bytes to stay put. A whole-source-in-memory buffer (loaded file, mmap, LMDB value) keeps slices valid as long as the buffer; a refill-window streaming source invalidates them as the parser advances.

## Decision

All four parsers are **hand-written streaming pull parsers over `[]byte`**, yielding one statement at a time, with **borrowed slices as the default representation of term strings** and **copy-on-write only where syntax forces it**. Concretely:

1. **Pull API**: the caller drives iteration — `parser_next(&p) -> (statement, ok)` (exact naming settled in the data-model initiative). No callback/push layer; one can be trivially built on top if wanted.
2. **Input is `[]byte`**: the parser consumes a caller-owned byte buffer. The caller decides whether that is a whole loaded file, an mmap, an LMDB value, or a refill window.
3. **Borrowed by default**: term strings in a yielded statement are slices into the source buffer whenever the token contains no escapes. The scanner detects escapes during tokenization, so the no-escape fast path allocates nothing.
4. **Copy-on-write for escapes**: only tokens actually containing escape sequences get an unescaped copy, allocated from a parser-configured allocator.
5. **Prefix/base expansion allocates** (Turtle/TriG): expanded IRIs are concatenated via the parser's allocator; repeated prefixed names should hit an intern table so each distinct IRI is materialized once per parse.
6. **Validity contract**: yielded statements are valid **until the next `parser_next` call or parser destruction, whichever comes first**. If the caller owns a stable whole-source buffer, pure borrowed slices happen to remain valid for the buffer's lifetime, but the API contract is per-statement — callers who keep terms must `clone`/intern them. This is the same discipline LMDB imposes on read transactions.
7. **Recursive descent for grammar**: Turtle/TriG's nested structures (collections, blank node property lists, graph blocks) are parsed by hand-written recursive descent on top of the zero-copy tokenizer. No parser generators, no grammar tables.
8. **No document materialization**: parsers never build an AST/DOM of the whole document. Parser-internal state is bounded by nesting depth and the prefix map, not document size.

## Alternatives Analysis

| Option | Pros | Cons | Risk Level | Implementation Cost |
|--------|------|------|------------|-------------------|
| Streaming pull parser, borrowed slices + CoW (chosen) | Zero/near-zero allocation on common path; LMDB-compatible discipline; caller controls iteration and memory; trivial to wrap as push | Lifetime contract callers must respect; slightly more complex term representation (borrowed vs owned) | Low | Medium |
| Push/callback (SAX-style) parser | Also streaming; simple parser-side control flow | Inverts caller control; awkward in Odin (closures/context plumbing); pull can't be recovered from push, while push over pull is trivial | Low | Medium |
| Materialize document into owned graph (DOM-style) | Simplest lifetime story; terms always owned | Unbounded memory on large documents; contradicts vision's streaming principle; forces copies the triplestore ingest path doesn't want | Medium | Low |
| Parser generator / table-driven grammar | Grammar traceable to spec EBNF | External tooling contradicts no-dependency constraint; poor fit for zero-copy tokenizing and Turtle's lexical quirks; harder error messages | High | High |

## Rationale

- **Pull over push**: the primary consumer is bulk ingestion (a future triplestore) and test-suite runners — both natural loops. Pull keeps the caller in control of pacing and allocation, matches Odin's iterator idioms, and a push adapter over pull is a five-line wrapper while the reverse requires threads or state machines.
- **Borrowed-by-default matches reality**: escapes are rare and prefix expansion is bounded and internable, so the vast majority of bytes flow from source to consumer without copying. A store ingesting triples immediately re-encodes terms into its own representation, so long-lived borrows were never needed.
- **Per-statement validity** is the weakest contract that supports both stable buffers and refill windows, so the API doesn't have to distinguish the two; it is also exactly the discipline LMDB users already accept.
- **Hand-written recursive descent** honors the vision's no-dependency constraint, gives precise spec-referencing error messages, and the four grammars are small and stable (W3C RECs), so generator leverage is minimal.
- Building N-Triples/N-Quads first exercises the fully-zero-copy path before Turtle/TriG add the allocating cases.

## Consequences

### Positive
- Near-zero allocation parsing for N-Triples/N-Quads; minimal allocation for Turtle/TriG.
- Direct compatibility with mmap'd files and LMDB read-transaction semantics.
- Bounded parser memory regardless of document size.
- One consistent API shape and lifetime contract across all four formats.

### Negative
- Callers must understand the borrow/clone contract; keeping a term past `parser_next` without cloning is a use-after-invalidate bug the type system won't catch.
- Emitting "zero-copy" as a feature obliges discipline in every later parser change (an accidental copy is a silent regression — benchmarks should guard this).
- Recursive descent for Turtle/TriG is more hand-written code to maintain than a generated parser.

### Neutral
- The data model must support borrowed term strings with an explicit `clone`/intern to promote to owned — this resolves the string-ownership question left open in RDF-I-0001 in favor of borrowed-by-default.
- "Zero-copy" is scoped honestly: *the parser never copies except unescaping and prefix/base expansion*, not literal zero allocation.
- True incremental refill (parsing a statement that straddles a window boundary) is left as a source-adapter concern, not a parser-core concern; the initial implementations may require whole-statement-in-buffer.
