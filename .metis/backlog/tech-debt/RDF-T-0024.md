# Decide and document the large-document streaming contract

## Objective

Decide whether whole-document-in-buffer is the library's documented input contract, or whether incremental-refill source adapters are needed before `odin-rdf-sparql` builds its ingestion layer on this library — and record the outcome. The vision's "streaming-friendly" principle says large documents shouldn't require the whole graph in memory; today parsing is statement-at-a-time with steady-state-zero allocation (no graph materialization), but it does require the whole document text in a caller-owned `[]byte`. The source-adapter question was explicitly deferred as a non-goal in RDF-I-0002 and never picked back up.

### Technical Debt Impact
- **Current Problems**: The gap between the vision's streaming principle and the actual whole-buffer contract is undocumented. Nothing states whether this is the intended final contract or a temporary limitation.
- **Benefits of Fixing**: `odin-rdf-sparql`'s loader design can commit to the real contract instead of guessing; either the docs close the question or the follow-up work gets scoped deliberately.
- **Risk Assessment**: If left implicit, downstream designs may assume refill semantics that don't exist, or conversely bake in whole-buffer assumptions that a later adapter layer would break.

## Implementation Notes

### Technical Approach
This is a decision-and-documentation task, not an implementation task. Inputs: ADR RDF-A-0001 (which frames refill as a source-adapter concern), the RDF-I-0002 non-goals, and the zero-copy/borrowing architecture. Note the hard case for adapters: statements straddling a buffer window (arbitrarily long literals), which interacts badly with borrowed slices. Note the strong argument for (a): on 64-bit targets a memory-mapped file gives whole-buffer semantics without RAM residency, which may satisfy the vision's principle as-is.

### Dependencies
None. Should be decided before or during [[RDF-T-0023]] so the documented contract is stated once, in the right place.

## Status Updates

**2026-08-04 — Analysis complete, decision pending ratification.**

Evidence gathered:
- All parsers take a caller-owned whole-document `[]byte` (`parser_init(p, source: []byte, ...)`); no refill/need-more-input machinery exists anywhere in `rdf/`.
- ADR RDF-A-0001 anticipated exactly this fork: input is `[]byte` and "the caller decides whether that is a whole loaded file, an mmap, an LMDB value, or a refill window"; per-statement validity was chosen as the weakest contract supporting both; true incremental refill was scoped as "a source-adapter concern, not a parser-core concern."
- The vision's streaming principle is about not materializing the *graph* — and that holds today: parser memory is bounded by nesting depth + prefix map, not document size.

Assessment of the two options:
- **(a) Whole-buffer contract, mmap for large files**: On 64-bit targets, mmap gives whole-buffer semantics without RAM residency — the document's bytes are paged in on demand. This matches the LMDB-driven design goal (stable mapped pages, borrowed slices). Both anticipated consumers (`odin-rdf-sparql` loading files, a future LMDB-backed store) have stable buffers; neither needs refill.
- **(b) Refill source adapters**: The hard case is a statement straddling the window boundary (arbitrarily long literals force either unbounded window growth or copy-out), and refill invalidates borrowed slices mid-parse — real complexity with no identified consumer. Network-stream ingestion is the only scenario that genuinely needs it, and no such consumer exists or is planned.

Recommendation: **(a)** — document whole-document-in-buffer as the input contract, name mmap as the intended path for large files, and defer adapters until a consumer with non-seekable input actually appears.

**2026-08-04 — DECIDED: option (a), ratified by Greger.**

Whole-document-in-buffer is the library's input contract. Memory-mapping is the intended path for large files (on 64-bit targets it gives whole-buffer semantics without RAM residency, and matches the LMDB zero-copy design goal from ADR RDF-A-0001). Refill source adapters are explicitly deferred — not tracked as backlog — until a consumer with genuinely non-seekable input (e.g., network streams) appears; if one does, adapter work starts from the per-statement validity contract, which was designed to accommodate it.

Vision RDF-V-0001's "Streaming-friendly" principle updated to state the contract. Propagation to user-facing docs happens in [[RDF-T-0023]] (package docs state the contract) and [[RDF-T-0022]] (README memory-model summary). Task complete.
