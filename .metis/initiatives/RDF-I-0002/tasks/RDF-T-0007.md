# N-Triples parser

## Parent Initiative

[[RDF-I-0002]]

## Objective

Implement the N-Triples parser in package `rdf/triples`: the resolved scanner-idiom API over the internal tokenizer, yielding borrowed `rdf.Triple` statements with copy-on-write unescaping.

## Acceptance Criteria

## Acceptance Criteria

- [x] `Parser` with `parser_init(p, source: []byte, allocator := context.allocator)`, `parser_next(p) -> (rdf.Triple, bool)`, `parser_destroy(p)`; after a `false` return, `p.err` distinguishes clean EOF from a syntax error.
- [x] Conforms to the W3C RDF 1.2 N-Triples grammar, including triple terms (`<<( ... )>>`, object position only, nesting supported).
- [x] Escape handling: ECHAR and UCHAR unescaping applied only to tokens whose `has_escape` flag is set, allocated from the parser's allocator and released by `parser_destroy`; statements without escapes allocate nothing (tracking-allocator test).
- [x] Errors use the shared `Error` struct (kind, offset, line, column) and a formatting proc references the violated grammar production; errors are sticky — after a syntax error, `parser_next` keeps returning `false` and parser state stays valid for reading `p.err`.
- [x] Statement validity contract documented on `parser_next`: yielded triples are valid until the next call or `parser_destroy` (per ADR RDF-A-0001); callers keep statements via `rdf.clone` or an `Intern_Table`.
- [x] Unit tests: representative valid documents (all term kinds, escapes, triple terms, comments, blank/whitespace lines), malformed inputs per error kind with expected positions, zero-allocation check; `odin check -vet -strict-style` clean.

## Implementation Notes

### Technical Approach
The statement-level parsing (subject/predicate/object/term recognition) should be written for reuse — N-Quads (RDF-T-0008) adds only the optional graph label, so this logic lands in the internal package or a form the quads package can call, not copy.

Sticky-error semantics chosen over skip-to-next-line recovery: simplest correct contract, and the W3C negative-syntax tests only need "document rejected". Line-level recovery can be added later without breaking the API.

### Dependencies
RDF-T-0006 (internal scanner).

## Status Updates

**2026-08-04**: Implemented and then factored for reuse. The statement-level core (subject/predicate/object recognition, literal parsing with lang/direction/datatype, recursive triple terms, copy-on-write unescaping, per-statement memory management, one-token lookahead, error helpers) lives in `rdf/internal/statement`; `rdf/triples` is a thin composition: `Parser` embeds `statement.Parser` via `using` (so `p.err` promotes cleanly), and `parser_next` is subject → predicate → object → dot. RDF-T-0008 will compose the quads grammar from the same core plus a graph-label step.

Implementation decisions:
- **CoW allocations are freed at the next `parser_next`**, not accumulated until destroy — memory stays bounded on escape-heavy documents and matches the per-statement contract exactly. Same for triple-term nodes.
- **Datatyped literals are built directly**, bypassing `rdf.literal_typed`'s assert: `"x"^^rdf:langString` is syntactically legal though semantically ill-typed, and grammar-driven construction must not crash on it.
- **Unescape buffer is sized to the escaped length up front** (decoded ≤ escaped), so it never reallocates and each unescaped string can be freed by pointer.
- **Direction split in the parser, not the scanner**: the Lang_Tag token carries `fr--ltr` whole; the parser splits on `--` and validates `ltr`/`rtl` (`Invalid_Direction` otherwise).
- Added `Expected_Datatype` to the shared `Error_Kind` (missed in the initial enum).

Tests: 8/8 (all term kinds, ECHAR/UCHAR unescaping, two-level nested triple terms, zero-allocation guard on an escape-free doc, CoW leak-freedom via tracking allocator, cross-line statements per the documented scanner decision, 11 negative cases incl. sticky errors, error line/column accuracy). All four packages `-vet -strict-style` clean; full test suite 31/31.
