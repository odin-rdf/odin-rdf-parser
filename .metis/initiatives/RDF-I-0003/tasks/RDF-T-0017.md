# TriG parser over the Turtle core

## Parent Initiative

[[RDF-I-0003]]

## Objective

Implement `rdf/trig` yielding `rdf.Quad`s: the full Turtle grammar (through the RDF 1.2 surface) plus graph blocks — `{ }` wrapped graphs with optional `GRAPH` keyword, IRI or blank-node graph labels, and default-graph statements — with the same public API shape as `rdf/quads`.

## Acceptance Criteria

## Acceptance Criteria

- [ ] All Turtle constructs from [[RDF-T-0014]]–[[RDF-T-0016]] parse inside graph blocks and in default-graph position, without duplicated production code.
- [ ] Graph blocks: `<g> { ... }`, `GRAPH <g> { ... }` (keyword case-insensitive), blank-node labels and `[ ]` as graph labels, empty blocks, and the grammar's block-vs-statement ambiguity (`{` after a term) resolved per spec.
- [ ] Default-graph statements outside blocks yield quads with the default-graph marker used by `rdf/quads`; directives apply document-wide regardless of block position.
- [ ] Public API mirrors `rdf/quads`: same init/next/destroy idiom, sticky structured errors, per-statement validity contract; sharing mechanism with `rdf/turtle` chosen and documented (thin layer over a shared internal parser core, mirroring how `rdf/nquads` layers over the statement core).
- [ ] Anonymous-label synthesis shares one counter across graphs so labels stay document-unique.
- [ ] Unit tests: each block form, Turtle structures inside blocks, TriG-specific error paths (nested graph blocks, quad-position triple terms if the grammar forbids them).

## Implementation Notes

### Technical Approach

Refactor the Turtle productions into an internal parser core parameterized by a statement sink (triple vs quad+graph-context), then make `rdf/turtle` and `rdf/trig` thin public layers — the same relationship `rdf/ntriples`/`rdf/nquads` have to `rdf/internal/statement`. The graph-context is a single field the TriG layer sets/clears around blocks.

### Dependencies

[[RDF-T-0016]] (complete Turtle core to layer over).

### Risk Considerations

The refactor to a shared core touches everything the previous three tasks built — do it as the first step of this task with the full Turtle test suite green before adding graph blocks. TriG's `{` ambiguity with annotation `{|` needs scanner-level care.

## Status Updates

**2026-08-04 — Completed.** `rdf/trig` package + graph-block support in the shared core; 8 trig tests and 3 new turtle-mode rejection tests pass, full suite green.

- **No refactor was needed**: the core was already in `rdf/internal/ttl` (decided in [[RDF-T-0014]]). TriG is a `trig_mode` flag plus `parse_block_start` and block state (`in_graph`, `current_graph`); Turtle mode is untouched and rejects `{`/`GRAPH` with the pre-existing errors.
- **Graph attachment mechanism**: the core records `current_graph` per statement; since the statement queue drains before any state transition, the trig layer simply pairs each yielded triple with `p.core.current_graph`. No statement-sink parameterization needed — simpler than the task sketch.
- **Ambiguities resolved**: `label { … }` vs `subject pol .` on the `'{'` lookahead after parsing the term; bare ANON `[] { … }` is a graph label while a non-empty `[ pol ]` never is (blankNodePropertyList requires a non-empty list); `{|` vs `{` was already a scanner-level two-byte token from [[RDF-T-0012]].
- **Grammar details**: final dot optional inside blocks (`triplesBlock`), dot required at top level; `GRAPH` keyword requires the wrapped form (`.Expected_Graph_Block`); EOF inside a block is `.Unclosed_Graph`; directives are top-level only (inside a block they fail as statements, matching the grammar).
- One control-flow bug caught during implementation: the label-turned-subject path fills the statement queue inside `parse_block_start`, so it must signal `parsed` to the statement loop — the first wiring would have re-parsed the token. Covered by `test_default_graph_and_blocks`.
