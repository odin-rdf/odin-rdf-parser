# Turtle scanner internal package

## Parent Initiative

[[RDF-I-0003]]

## Objective

Implement the Turtle/TriG scanner as an internal package tokenizing the full W3C RDF 1.2 Turtle lexical grammar with source positions, reusing the existing escape-validation and position primitives as functions while sharing no scanner state machine with the line-based scanners (per the RDF-I-0003 design decision).

## Acceptance Criteria

## Acceptance Criteria

- [ ] Tokenizes every RDF 1.2 Turtle terminal: `IRIREF`, `PNAME_NS`/`PNAME_LN`, `BLANK_NODE_LABEL`, punctuation `[ ] ( ) ; , .`, directives (`@prefix`, `@base`, case-insensitive `PREFIX`/`BASE`), `a`, `true`/`false`, numeric forms (`INTEGER`/`DECIMAL`/`DOUBLE`), all four string forms (single/double-quoted, short/long), `LANGTAG` including RDF 1.2 base directions (`@en--ltr`), and the RDF 1.2 punctuation `<<`, `>>`, `<<(`, `)>>`, `{|`, `|}`, `~`; comments and whitespace skipped correctly.
- [ ] Tokens are zero-copy slices into the input and carry line/column positions consistent with the existing parsers' error model.
- [ ] Escape validation (`\u`/`\U`, string escapes, `PN_LOCAL` reserved-character escapes) reuses `rdf/internal` primitives as functions; unescaping is deferred to the parser (CoW discipline).
- [ ] Unit tests cover every terminal plus error cases (unterminated strings, bad escapes, illegal codepoints in `PN_CHARS`); allocation guard confirms scanning allocates nothing.
- [ ] Token inventory documented in this task; the shared-conventions-not-code scanner decision confirmed or revisited with rationale in Status Updates.

## Implementation Notes

### Technical Approach

Hand-written byte-oriented scanner in `rdf/internal`, same style as the line-based scanners. Token = kind + span + position. The `.` terminal is context-sensitive (statement terminator vs `DECIMAL`/`DOUBLE` vs trailing-dot rules in `PN_LOCAL`); resolve with bounded lookahead in the scanner where the lexical grammar allows it, and document any cases that need parser cooperation.

### Dependencies

Existing `rdf/internal` escape-validation and position primitives. No other RDF-I-0003 task.

### Risk Considerations

`PN_CHARS_BASE` Unicode ranges are fiddly — test boundaries explicitly. Long-string scanning needs quote-run lookahead. The `.` disambiguation is the classic Turtle scanner trap; keep the rules in one commented place.

## Status Updates

**2026-08-04 — Completed.** New package `rdf/internal/ttl` (`token.odin`, `scanner.odin`, `scanner_test.odin`); 17 tests pass, full repo suite still green.

- **Token inventory** (see `token.odin`): IRI_Ref, PName (single kind for PNAME_NS/PNAME_LN — split at first colon, which is always the separator since PN_PREFIX cannot contain ':'), Blank_Node_Label, String_Literal (one kind for all four quoted forms), Lang_Tag (direction suffix included), Integer/Decimal/Double/Boolean, A, At_Prefix/At_Base, Sparql_Prefix/Sparql_Base, Graph_Keyword, Datatype_Marker, Dot/Semicolon/Comma, brackets/parens/braces, Reified_Open/Close (`<<`/`>>`), Triple_Term_Open/Close (`<<(`/`)>>`), Annotation_Open/Close (`{|`/`|}`), Tilde.
- **Sharing decision confirmed**: shares `Error`/`Error_Kind` (extended with 4 Turtle kinds in `rdf/internal/scanner/error.odin`) and the character classifiers `is_alpha`/`is_alnum`/`is_hex_digit` (made public) — no scanner state machine shared, as designed.
- **`.` disambiguation** resolved entirely in the scanner: number only when digits or a verified exponent follow (`1.5`, `.5`, `1.e0`); dot runs inside PN_PREFIX/PN_LOCAL/blank-labels are content only when a name character follows the run (handles `a..b` without emitting a trailing dot). No parser cooperation needed.
- **Maximal-munch compound tokens verified safe**: no legal production puts `(` after `<<` or a collection close directly before `>>`, so `<<(`/`)>>` cannot mis-tokenize valid input (reasoning in scanner.odin comments).
- **`@prefix`/`@base` vs LANGTAG**: reserved only in exact bare form; `@prefix-x` scans as a language tag by maximal munch.
- **PN_CHARS is exact** (full rune ranges), deliberately stricter than the line scanner's loose byte check — the Turtle suites exercise it. Zero-allocation scanning asserted by test.
- Note for [[RDF-T-0016]]: `<<` vs `<<(` lookahead already handled here.
